FreeFSM v1: pairing, sessions, Job sync and field protocols

Local OpenAPI 3.1 · Interactive reference harness

Password-free pairing

  1. POST /api/v1/pairings with a device_name (1–100 characters) and new UUID operation_id. Keep device_code private in memory; show user_code.
  2. The user opens /pair in an authenticated browser, enters user_code and reviews the device label. Approve only the intended device. Browser CSRF and forced password replacement remain mandatory.
  3. After explicit approval, POST /api/v1/pairings/redeem with device_code and a new UUID operation_id. A 201 response delivers the opaque bearer once. Never send an account password to the API.

Pairing expires exactly ten minutes after creation, including approved pairings. Device and user codes are distinct random secrets stored only as hashes. Re-review replaces the browser-bound confirmation. A different browser cannot confirm it. Cancellation uses POST /pairings/cancel with device_code and a UUID operation_id; same-ID retries have no additional effect. Cancellation and redemption serialize: only the winning action takes effect. Approved pairings are invalid if the approving browser/account becomes invalid or its password changes before redemption.

Do not automatically repeat an interrupted approval or redemption. A lost successful bearer response cannot be recovered: inspect/revoke the labelled session in /sessions, then explicitly pair again. Replayed operation IDs never create a second session. Protocol tombstones are durable; this protocol does not depend on field-mutation receipts.

Session and recovery guide

Send Authorization: Bearer <token>. Mobile sessions expire after 30 days of inactivity, extended only by successful online authorization. Offline work cannot renew them; there is no refresh token. Browser login lasts a fixed seven days. GET /sessions lists your sessions; DELETE /sessions/{sessionID} revokes one, DELETE /session logs out the current bearer, DELETE /sessions revokes all your sessions. The hosted /sessions page also supports these actions.

Every API session DELETE requires one client-generated UUID Operation-ID header and no body. Unchanged retry retains the original ID and exact route/target; changed intent requires a new reviewed ID. GET /session-operations/{operation} returns the immutable nonsensitive receipt. Self revocation immediately invalidates the bearer, even for receipt lookup: authenticate afresh as the original user to reconcile, never automatically replay. Fresh authentication permits receipt reading but cannot rebind the original client's operation.

POST /time-entries/lease requires an empty JSON object and Operation-ID. GET /clock-lease-operations/{operation} reconciles the original same-client issuance after response loss. Receipt replay returns the original lease UUID and bounds, never a renewed window, even after expiry. An explicit new renewal uses a new operation UUID. Current identity and clock authority still govern acceptance; leases cannot bypass grant loss.

Disablement, required credential replacement, explicit revocation, Administrator/email reset and restore invalidate sessions. Self password change retains only the acting browser. Use the hosted recovery page or contact an Administrator when email is unavailable. The API never takes recovery passwords and never discloses whether an account exists.

Remember X-FreeFSM-Session-Epoch only after authenticating. Present it on later private requests. instance_restored means lock recoverable pending intent for fresh authentication, synchronization and explicit review; never automatically replay. Ordinary unauthorized/password_change_required means purge cached credentials/data. Public discovery and pairing disclose no deployment epoch.

Limits, CORS and errors

Defaults per sliding minute: 5 authentication attempts per normalized (trimmed, lowercase) login, 20 per IP, 300 requests per authenticated user across devices, 12 synchronization requests per client bearer. Hosted authentication applies login and IP budgets; password-free pairing applies IP budgets. GET /capabilities publishes effective grants and limits only after authentication. Limits are budgets, not throughput guarantees. Additional abuse controls may apply.

Operator environment settings: FREEFSM_AUTH_PER_LOGIN, FREEFSM_AUTH_PER_IP, FREEFSM_API_PER_USER, FREEFSM_API_SYNC_PER_CLIENT (positive integers). Budgets are process-local and reset on restart. Use a single serving process or an upstream shared abuse budget when running multiple processes. CORS defaults off. FREEFSM_API_CORS_ORIGINS is a comma-separated list of exact HTTPS origins, without paths, wildcard, user information or trailing slash. No cookies or credentialed CORS. Preflight permits GET/POST/PUT/PATCH/DELETE and Authorization, Content-Type, Operation-ID, X-FreeFSM-Session-Epoch, Range, If-Range and If-None-Match only. Same-origin access needs no CORS grant.

Errors contain error.status (the numeric HTTP status), code, message, request_id, safe details and recovery_disposition. Retryable errors include retry_after_seconds and Retry-After in seconds; preserve the original operation ID and exact intent. Interpret codes, not prose; reconcile uncertain outcomes before explicit retry. Unknown codes/enums require explicit review, never assume success. Unknown request fields/types/filters are rejected; ignore unknown response fields. JSON requests are bounded to 1 MiB.

Authorized Job synchronization

GET /api/v1/sync/jobs reads a coherent authorized snapshot, then state-comparison deltas. Authenticate with the paired bearer. Query parameters: scope=assigned (default) or all (requires Job View A); page_size is an integer 1–200 (default 50); page is a returned next-page token; cursor is a fully applied completion token. Keep scope and page_size identical throughout a chain. Parameters occur at most once, must be nonempty, and page/cursor are mutually exclusive. Unknown parameters, types, scopes and repeated parameters return 400 invalid_request; there is no query expansion.

GET /capabilities publishes authenticated sync availability, scopes, filters, 50/200 page bounds and 30-day continuity. The default 12-sync-per-minute-per-client budget applies to pages and replays. Discovery is not authority: every page rechecks current grants, assignment and context relationships.

The data envelope contains records (complete Job replacements), removed (opaque Job identities only), watermark (RFC3339), next_page, completion_cursor, complete and purge (none). Nonfinal pages have next_page and null completion_cursor; final pages have completion_cursor and null next_page. Begin without tokens, replacing the selected scope. Stage and apply all pages; atomically commit each page with its continuation metadata. Promote completion_cursor only after successful complete local application. Subsequent deltas catch changes committed during pagination. Replay upserts opaque identity without adding copies or history; deltas are state, not audit events.

Purge removed IDs from both committed and staged data, including prior snapshot pages. Complete replacements remove omitted old facets. A network, malformed-JSON, server-storage or local-application failure remains incomplete/retryable: keep the prior completed cursor, retry the same request, never skip a page. Authority purges cannot be rolled back by a local failure.

Every tokenless request creates a new snapshot, including first-page replay and retry after network or local failure. Discard old cache and staging before sending it; never merge its records into a prior materialization. Its removed list has no prior snapshot baseline.

Continuity is retained for at least 30 days. Expired, unknown, cross-client, filter-mismatched or unsafe tokens and changed grants return 409 resnapshot_required, recovery_disposition=purge_and_resnapshot and details={purge:all}. Discard all cached Job/context and tokens, then start without tokens. Observed assignment/deletion loss durably invalidates existing continuity for the authenticated user/session, including already-created successors. Unchanged reassignment never revives these tokens; a fresh snapshot restores currently authorized Jobs with unchanged opaque identities. Replaying an invalidated token does not invalidate later fresh snapshots. Ordinary 401 purges credentials/cache; 403 purges Job/context. Purge on denial even if its JSON body is damaged. For 429/503 observe Retry-After and retry explicitly without advancing completion. Restore recovery remains locked review, not automatic replay.

Job records contain opaque id, title, description, field_notes, status name/category, nullable schedule/due/arrival values, IANA timezone, optional Customer and closed masters. Customer includes operational names/Kind/phone/email/Service Notes; explicit Contacts include name/role/phone/email/Service Notes; Location includes service address/coordinates/Access/Service Notes; operational Assets include Number/name/class/type/status/serial/manufacturer/model/installed-warranty dates/current Location/Service Notes; Project includes name/description/Status/progress/planned dates/linked Location/Service Notes. Without independent archived detail authority, an archived Project is only project_reference with name and archived=true. All context requires explicit current assignment and facet grants, even for All Records users.

Exact closed nested schemas are in OpenAPI. This synchronization slice is read-only: no billing, internal notes, master fields, siblings, recursive collaboration, Items, Service Entries, Lease coverage or unrestricted history are included. Authorized field reads/revisions/capabilities, mutations, receipts, File transfer and offline staging use their separate contracts and endpoints; sync does not grant mutation or offline authority. Sync IDs are opaque/nonreused; instants RFC3339 with offsets; dates ISO YYYY-MM-DD; timezone IANA. No monetary or mutation occurrence/acceptance values are invented. Ignore unknown response fields and handle unknown enums safely; never infer authority or an action.

Job Status and Field Notes

GET /jobs/{id}/status-intents supplies status_id, status_revision and meaning_revision. POST /jobs/{id}/status sends those tokens and a new operation_id. GET /jobs/{id}/field-notes supplies field_notes and notes_revision; POST to the same path sends both with a new operation_id (explicit empty text clears it). The grants job.status and job.field_notes.edit are independent J/A actions with Job View. Completed/Canceled remain actionable; archive is read-only.

Receipts and common operation admission have no expiry (at least 30 days); effect identity is retained for its lifetime. Field Notes, original attribution, revision, history, activity, audit and terminal receipt commit together. A current-revision identical-text save preserves the original effect and attribution. The receipt contains only operation_id, code, accepted_at and an optional effect_id, never Notes text or Job metadata. After response loss and access removal, query GET /job-execution-operations/{operation} before deciding what happened. The original authenticated user may reconcile after fresh sign-in; that never rebinds the old command to a new client.

The executable job-execution.js reference locks unknown transport outcomes until original-ID reconciliation. Receipt lookup never submits a mutation. Whole-instance restore can remove post-backup receipts and effects: absence does not prove failure. Logout and ordinary failed authorization purge intent. The website remains online-only.

Same valid Status is a no-op; rename is safe, changed category/identity requires explicit reselection. Stale different Status and stale notes (including ABA) reject. GET /jobs/{id}/field-notes/history returns immutable current-authority history; migration baseline null author/time is unknown, not an invented edit. Unattributed legacy text requires protected Administrator review in the browser.

The original user can read nonsensitive receipt code/effect_id/accepted_at after scope loss or fresh sign-in. Terminal repair requires a new explicitly reviewed ID; transient failure retries the original unchanged ID. No force, merge, auto-reselection or inference of failure from missing receipts after restore. Resumable Files, integrity and scoping

Authenticated GET /files/limits discovers max_file_bytes (default 25 MiB, operator FREEFSM_MAX_UPLOAD_SIZE in bytes), max_chunk_bytes (1 MiB), max_batch_files (10), and SHA-256. Transfer JSON is bounded to 16 KiB; raw chunks to 1 MiB. Queue outcomes are independent; retained successes are not resent.

  1. POST /file-transfers with nonzero UUID id and publication_id, original object_type (job, estimate, invoice), object_id, name, positive size and lowercase exact-byte sha256. Supply an independent client-generated Operation-ID UUID header, distinct from both transfer id and publication_id. The API permits only Job-bound parents.
  2. PUT /file-transfers/{id}/chunks?offset=N with raw bytes, contiguous segments of 1 through 1048576 bytes, and an independent Operation-ID UUID for each new chunk intent. Stage that UUID, offset and exact bytes before sending. Exact replay retains the same operation header; repaired intent requires a new UUID. GET /file-transfers/{id} discovers currently authorized durable progress. Changed intent, overlap or gaps reject.
  3. POST /file-transfers/{id}/verify checks complete bytes and the shared File content-extension validator. verified:true is a fresh observation, not a stored certificate. Transport status alone always has verified:false. Complete temporary transfers create no ordinary File or collaboration history. Publication is a separate operation.

After response loss, reconcile GET /file-transfer-operations/{operation} before retrying. The envelope data contains operation_id, transfer_id, code and accepted_at (rejections may omit transfer_id). This safe scoped receipt remains available after parent access loss; reading the transfer representation still requires current authority. Accepted receipts need no write replay; terminal rejection requires explicit review and a new operation UUID for repaired intent. An unavailable lookup leaves the outcome unknown and blocks replay. A confirmed receipt miss permits explicit replay of the exact staged intent and header. The queue retains pending start/chunk IDs and exact segment bytes in memory across retries, skips retained successes, and never blindly replays unknown outcomes.

PNG, JPEG, GIF, WebP, PDF, text, CSV, legacy/OpenXML Office, ODT, ODS, ZIP and JSON use the same validator as ordinary uploads; ZIP is never extracted. Transfers survive process restart in PostgreSQL. Resume has no automatic time expiry, but is always bounded by the original paired session, current authority and current operator limit. A revoked/expired session has no resume exception.

POST /file-transfers/lookup with original object_type, object_id and sha256 only finds the caller's own paired-session transfer at that parent, reverified before return. Reuse the returned unchanged identity; never clone/retarget pending intent. Digests and UUIDs reveal no cross-user or inaccessible-parent content. No global digest lookup exists.

GET /files/{id} verifies a restricted snapshot before serving; missing bytes or recorded digest mismatch fail explicitly. Repr-Digest (sha-256 base64) covers the entire representation; ETag is its strong digest identity. Use Range and If-Range for segments and verify the final assembled digest. A mismatched If-Range returns the complete representation, not a segment to append. Legacy Files with no recorded digest retain NULL; response integrity describes current observed bytes only. Exact allowed CORS origins support Range, If-Range, If-None-Match and expose ETag, Repr-Digest, Content-Range and File-Revision.

Errors: 400 invalid_file/invalid_offset/invalid_request, 401 unauthorized, 403 forbidden on a visible parent, 404 not_found for an invisible transfer/parent or scoped digest miss, 409 file_conflict for incomplete or inconsistent resume, 413 chunk_too_large, 429 rate_limit_exceeded, 500 file_unavailable for durable-storage/audit failure (retry disposition), 503 unavailable for admission/dependency failure. Never interpret an error as successful verification or publication; reconcile the original operation receipt before explicitly retrying unchanged intent. All writes recheck authority under the shared commit fence and record immutable transport audit atomically, without ordinary collaboration events.

Reference harness and changelog

The harness is a deliberately small interactive protocol exerciser, not a production client. It stores secrets only in closure memory, omits browser cookies on API calls, does not print bearers, persist cache, register a service worker, or automatically replay actions. Reloading discards its credential. Its File queue supports explicit failed-item retry and does not publish. Production clients need platform-protected token/cache storage and the field protocol's purge/reconciliation rules. Exact commercial amounts

Blank browser adjustment fields mean no adjustment. An explicit typed zero remains a recorded adjustment and survives metadata-only edits; it is not silently removed by editor serialization.

POST /estimates or /invoices creates a Job-bound document with operation_id, client_id and job_id. PATCH /estimates/{id} or /invoices/{id} uses a fresh operation_id and the reviewed whole-commercial revision. Reconcile GET /commercial-operations/{operation} before retrying an uncertain save; never repair an old intent in place. Independent captured-pricing authority protects monetary inputs and results.

Use positive plain-decimal strings for quantity and signed two-decimal USD strings for unit_price. Compatible finite JSON numeric quantities retain their decimal tokens, including scientific notation; strings are recommended to avoid client-side float loss. Reads return quantities as strings. Each line accepts discount_adjustment and surcharge_adjustment, independently {"kind":"fixed","value":"1.00"} or {"kind":"percentage","value":"10"}. Legacy fixed discount/surcharge string aliases remain accepted; a nonzero alias cannot accompany a typed adjustment of the same kind. Negative-price lines cannot carry typed adjustments.

{"operation_id":"b157d50e-5097-42be-a462-e46888e77608","client_id":"c3656fb5-86ef-47bf-8ec0-d46422687a96","job_id":42,"title":"Reviewed work","tax_rate":"10","line_items":[{"title":"Fractional work","quantity":"0.335","unit_price":"3.00","taxable":true,"discount_adjustment":{"kind":"percentage","value":"50"},"surcharge_adjustment":{"kind":"percentage","value":"10"}},{"title":"Tax rounding","quantity":"1","unit_price":"0.05","taxable":true}]}

This example accepts subtotal $0.61, tax $0.07 and total $0.68. Round base and each adjustment result half away from zero to cents; discount floors at zero before surcharge. The document adjustments object independently replaces its discount and surcharge; {} clears both. Allocate each stage across current positive lines by largest remainder, resolving ties by original line order. An exhausted discount caps at the positive pool; a nonzero fixed surcharge with no positive targets rejects. Percentage surcharge on a zero pool is a zero monetary effect. One tax rate (0–100) applies to adjusted taxable lines; current Customer exemption is captured at monetary commit.
