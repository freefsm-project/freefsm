FreeFSM v1: pairing, sessions and Subtasks

Local OpenAPI 3.1 · Interactive reference harness

Password-free pairing

  1. POST /api/v1/pairings with a device_name (1–100 characters) and new UUID operation_id. Keep device_code private in memory; show user_code.
  2. The user opens /pair in an authenticated browser, enters user_code and reviews the device label. Approve only the intended device. Browser CSRF and forced password replacement remain mandatory.
  3. After explicit approval, POST /api/v1/pairings/redeem with device_code and a new UUID operation_id. A 201 response delivers the opaque bearer once. Never send an account password to the API.

Pairing expires exactly ten minutes after creation, including approved pairings. Device and user codes are distinct random secrets stored only as hashes. Re-review replaces the browser-bound confirmation. A different browser cannot confirm it. Cancellation uses POST /pairings/cancel with device_code and a UUID operation_id; same-ID retries have no additional effect. Cancellation and redemption serialize: only the winning action takes effect. Approved pairings are invalid if the approving browser/account becomes invalid or its password changes before redemption.

Do not automatically repeat an interrupted approval or redemption. A lost successful bearer response cannot be recovered: inspect/revoke the labelled session in /sessions, then explicitly pair again. Replayed operation IDs never create a second session. Protocol tombstones are durable; this protocol does not depend on field-mutation receipts.

Session and recovery guide

Send Authorization: Bearer <token>. Mobile sessions expire after 30 days of inactivity, extended only by successful online authorization. Offline work cannot renew them; there is no refresh token. Browser login lasts a fixed seven days. GET /sessions lists your sessions; DELETE /sessions/{sessionID} revokes one, DELETE /session logs out the current bearer, DELETE /sessions revokes all your sessions. The hosted /sessions page also supports these actions.

Disablement, required credential replacement, explicit revocation, Administrator/email reset and restore invalidate sessions. Self password change retains only the acting browser. Use the hosted recovery page or contact an Administrator when email is unavailable. The API never takes recovery passwords and never discloses whether an account exists.

Remember X-FreeFSM-Session-Epoch only after authenticating. Present it on later private requests. instance_restored means lock recoverable pending intent for fresh authentication, synchronization and explicit review; never automatically replay. Ordinary unauthorized/password_change_required means purge cached credentials/data. Public discovery and pairing disclose no deployment epoch.

Limits, CORS and errors

Defaults per sliding minute: 5 authentication attempts per normalized (trimmed, lowercase) login, 20 per IP, 300 requests per authenticated user across devices, 12 synchronization requests per client bearer. Hosted authentication applies login and IP budgets; password-free pairing applies IP budgets. GET /capabilities publishes effective grants and limits only after authentication. Limits are budgets, not throughput guarantees. Additional abuse controls may apply.

Operator environment settings: FREEFSM_AUTH_PER_LOGIN, FREEFSM_AUTH_PER_IP, FREEFSM_API_PER_USER, FREEFSM_API_SYNC_PER_CLIENT (positive integers). Budgets are process-local and reset on restart. Use a single serving process or an upstream shared abuse budget when running multiple processes. CORS defaults off. FREEFSM_API_CORS_ORIGINS is a comma-separated list of exact HTTPS origins, without paths, wildcard, user information or trailing slash. No cookies or credentialed CORS. Preflight permits GET/POST/PUT/PATCH/DELETE and Authorization, Content-Type, X-FreeFSM-Session-Epoch only. Same-origin access needs no CORS grant.

Errors contain error.code, message, request_id, details, recovery_disposition and optional retry_after_seconds. HTTP 429 also has Retry-After in seconds. Interpret codes, not prose; retry only when safe. Unknown codes/enums require explicit review, never assume success. Unknown request fields/types/filters are rejected; ignore unknown response fields. JSON requests are bounded to 1 MiB.

Compatibility and reconciliation examples

POST /pairings
{"device_name":"Field tablet","operation_id":"120572ae-6ce2-4b16-8213-dc12f7e19d50"}

409 {"error":{"code":"pairing_unavailable", ...}}
→ Pending, consumed, expired, cancelled or authority lost: inspect browser state; do not infer issuance.
429 + Retry-After: 60
→ Wait; do not assume reserved capacity.
401 + recovery_disposition: locked_review
→ Fresh browser pairing, current-authority synchronization, explicit pending-intent review.
503 + recovery_disposition: retry
→ No success acknowledged; an uncertain commit may already have consumed pairing. Never create repeated sessions blindly.

Domain mutation receipts, offline conflicts, synchronization cursors and resumable File effects have their own endpoints; pairing is not a generic mutation receipt. Never reuse a pairing operation ID for field effects. The website remains online-only. No client may infer authorization from a Role label or capability listing; every action checks current authority.

Job Status and Field Notes

GET /jobs/{id}/status-intents supplies status_id, status_revision and meaning_revision. POST /jobs/{id}/status sends those tokens and a new operation_id. GET /jobs/{id}/field-notes supplies field_notes and notes_revision; POST to the same path sends both with a new operation_id (explicit empty text clears it). The grants job.status and job.field_notes.edit are independent J/A actions with Job View. Completed/Canceled remain actionable; archive is read-only.

Same valid Status is a no-op; rename is safe, changed category/identity requires explicit reselection. Stale different Status and stale notes (including ABA) reject. GET /jobs/{id}/field-notes/history returns immutable current-authority history; migration baseline null author/time is unknown, not an invented edit. Unattributed legacy text requires protected Administrator review in the browser.

GET /job-execution-operations/{operation_id} reconciles the original terminal receipt after response loss. Same intent never duplicates; changed intent rejects. The original user can read nonsensitive receipt code/effect_id/accepted_at after scope loss or fresh sign-in. Terminal repair requires a new explicitly reviewed ID; transient failure retries the original unchanged ID. No force, merge, auto-reselection or inference of failure from missing receipts after restore. Executable offline Job reference module stages without transport, enforces a supplied lease expiry, reconciles IDs, and purges inaccessible intent; it is exercised against real HTTP by the persisted browser acceptance test.

Stable Job Subtasks

GET /jobs/{id}/subtasks returns currently authorized UUID-identified active entries, their independent completion_revision and attributable history. A pending legacy review is explicit; positional rows are never valid field targets. Complete/Reopen have separate current Assigned Jobs or All Records grants. Active Completed/Canceled Jobs remain actionable. Checklist maintenance is browser-only.

PATCH /jobs/42/subtasks/90f8a7ab-8bcb-4c39-a591-4771e980e70a
{"operation_id":"f01d49a0-13c8-41a1-8555-cd53126ff9c4","completion_revision":"980c148b-99fc-43a4-9403-5b047d7962b3","completed":true}

GET /subtask-operations/f01d49a0-13c8-41a1-8555-cd53126ff9c4

Rename/reorder never invalidate completion revision. Same-state completion/reopening preserves attribution; stale opposite-state or ABA returns subtask_conflict. Removal cannot be undone by stale intent. After a lost response, query the original operation receipt before explicitly retrying the same intent/ID. Changed-intent reuse conflicts. Terminal repair requires fresh authorized state and a new reviewed operation ID. Receipts retain nonsensitive disposition/effect identity after Job access loss, bound to the same authenticated user/client; they never disclose checklist text or history. Retryable storage/audit failures create no terminal receipt. Optional occurred_at is client evidence, not authority or server acceptance time.

The source-distributed Node module reference/subtasks-reference.cjs and executable HTTP conformance test demonstrate disconnected staging and receipt reconciliation. The caller supplies staging authorization. They are not a production offline cache, lease or batch-sync implementation.

Reference harness and changelog

The interactive pairing harness is a deliberately small protocol exerciser, not a production client. It stores secrets only in closure memory, omits browser cookies on API calls, does not print bearers, persist cache, register a service worker, or replay actions. Reloading discards its credential. Production clients need platform-protected token/cache storage and the field protocol's purge/reconciliation rules.

v1 initial publication: browser-approved pairing replaces POST /session password login (410 pairing_required). After publication, v1 changes are additive; breaking contracts require a new major. Pre-v1 contracts have no compatibility guarantee.
